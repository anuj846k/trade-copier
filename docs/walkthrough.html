Read me first

The honest one-paragraph summary: the copier is real and it runs — you can start it against PostgreSQL, seed three accounts, and watch a master trade get sized per risk model, mapped across broker symbol suffixes, written to a durable outbox and "filled" by a mock connector, with P/L attributed back to the link. That path is covered by 234 tests and it is the part I would defend in review.

The part I would not defend is anything that needs a real broker. MT4/MT5 expose no supported server-side API, so the terminal side is an Expert Advisor that polls a local agent. I wrote that EA against the documented MQL5 API and this repo's own agent contract, and it has never been compiled — there is no MetaTrader in this environment. Same for the vendor's "20–30 ms" latency claim: I did not reproduce it, and this design cannot achieve it, so it is not repeated anywhere in the repo.

If you read only four things:

  1. §7 Six defects found by running it — the four runtime bugs all lived in code that type-checked and looked correct. That is the most useful lesson here.
  2. §4 The unknowns — what the reference product does not say publicly, and how each gap was handled without guessing.
  3. §8 The sizing formulas — writing these down is what exposed that my first draft of the docs was wrong, not the code.
  4. §9 Verified vs unverified — the exact boundary of what is proven.

1. The method

The working discipline came from REA — “Reverse Engineer Anything” (github.com/morluto/rea, MIT), checked out locally into rea/ and gitignored — it is tooling, not part of the app. I did not use its binary/runtime instrumentation (there was no binary to instrument: the reference is a hosted SaaS). What I took is its epistemic discipline, which is what actually matters when the thing you are reverse-engineering is a product rather than an executable:

  1. Evidence before conclusions. Fetch, cache and quote the primary source. Never let a summary of a source replace the source.
  2. Tag every conclusion by how you know it. Four tags, and only four: Observed stated by a first-party source; Derived a direct consequence of an observation; Inferred an engineering requirement for this class of product, flagged as unverified; Unknown could not be verified — so it is not guessed.
  3. Unknowns are deliverables. An unknown written down and handled deliberately is worth more than a plausible invention that nobody can distinguish from fact.
  4. Result algebra over exceptions. Model expected failures as values, so the “everything is a special case” parts stay in one shape.
  5. Dependencies flow inward. A pure core that knows nothing about the database, the network or a logger.

The output of step 1–3 is FEATURES.md: 66 features (F1–F66), 11 behavioural rules extracted as test oracles, and 11 explicit unknowns (U1–U11). It was committed before the implementation — commit 08a0f13 — so the spec could not be retro-fitted to whatever the code ended up doing. That ordering is the whole point: it makes the ledger falsifiable.

How the method paid off. Two things stand out in hindsight. First, tagging Derived vs Inferred forced me to notice that “close events must be mirrored” is a consequence of “trades are mirrored”, whereas “reconcile slave state after a disconnect” is not stated anywhere — which is exactly why reconciliation ships off by default (U7). Second, having U1 (the latency claim) written down as an unknown meant I did not quietly inherit a marketing number into a sync interval.

Everything else — the stack, the layering, the money maths, the wire protocol — is in §6 as decision cards, each with the reason and the alternative I rejected, because the rejected alternative is usually the more interesting half.

Where a library genuinely was the right call, it is a published package with a permissive licence, listed above. There is no copied GPL or unlicensed code in this repository — which matters, because origin is public.

4. The unknowns

This is the part of the method I would most defend. When the public documentation stops, the options are: invent something plausible, or write down that you do not know and choose a default that fails safe. Each of these is one of the four tags from §1 — mostly Unknown — and each has a stated handling.

#UnknownHow this build handles it
U1What the “20–30 ms” latency claim actually measuresNot reproduced and not repeated. The engine measures and logs real per-command latency; the agent's minimum copy latency is the poll interval plus broker execution, and docs/BRIDGE.md says so.
U2Their internal architecture, queueing, worker topologyReplaced by a design of my own, written down in docs/ARCHITECTURE.md — stated as this system's architecture, never as theirs.
U3Whether execution is routed through colocated cloud hostsNot implemented. The bridge agent dials out; deployment topology is the operator's choice.
U4What Balance Multiplier does when master and slave contract sizes differ (“align contract sizes” is all the docs say)Turned into an explicit formula with a switch: Contract Alignment, default-on for the balance multipliers, off otherwise, and a warning log when sizes differ with it off.
U5Whether a master partial close is mirrored proportionally, FIFO, or unsupportedImplemented proportionally — and flagged as an assumption in README.md, because a proportional close is the one that preserves the follower's risk ratio.
U6The exact “Hold / Expiry” semantics of Copy Expiry Time across platformsModelled as an absolute UTC expiry carried to the slave; a platform that cannot express it reports the capability flag and the command is refused rather than silently dropped.
U7Whether they reconcile slave state after a disconnectNot documented ⇒ implemented as off by default. Reconnect schedules a reconcile that logs RECONNECT_MISMATCH; actually reopening a missing position (reopenMissing) is opt-in, because a delayed broker view would otherwise get a second position — worse than a missing one.
U8Subscription/payment internals: proration, refunds, invoicesPlans and entitlements exist as data and are enforced; there is no payment provider. Stated plainly in docs/MANUAL-STEPS.md § 8.
U9Mobile apps, community Rooms, the Analyzer's exact metric definitionsOut of scope; the analytics module covers the documented metric list (F59–F60) only.
U10Their security internals — 2FA, session policy, encryptionNot documented ⇒ standard hardening applied and written up in docs/SECURITY.md: scrypt, rotating refresh tokens, TOTP, AES-256-GCM, single-use WS tickets, rate limits.
U11Their notification-template rendering engineReproduced the documented %TOKEN% substitution behaviour and nothing beyond it.

U4 and U7 are the two that shaped code the most. Both were cases where the “obvious” answer is dangerous: assuming a contract-size convention would misprice every gold copy, and auto-reopening a missing position turns a delayed broker response into a doubled position. Writing the unknown down first is what made the safe default visible.

Scope, stated as a boundary

In scope: the forex/CFD copier (F1–F9 except infra provisioning, F10's MT4/MT5 path plus a generic adapter seam, F14–F66 with F63's entitlement enforcement but no gateway). Explicitly out: futures platforms (F11), cloud/VPS provisioning (F9), mobile (F13), Rooms, and any payment integration (U8). Report-style flags like F12 (“100% cloud, no EA/VPS install for the user”) are observed but not reproduced — this build ships a cloud API plus a small agent on the user's machine, and §6.6 explains why that is the honest architecture rather than a shortcut.

6. Decisions and rationale

One card per decision: what was chosen, why, and what was rejected. The rejected option is usually the one that reveals the constraint.

6.1 Method & contracts

Zod schemas in a shared contracts package are the single source of truth

The same shapes ride HTTP, the WebSocket frames and the browser, and they must be validated on arrival, not only on send. One definition means the API cannot accept a field the dashboard cannot send, or vice versa. The route handlers, the BFF and the client all import them.

Rejected: per-app type definitions (three chances to disagree), and OpenAPI-first (a codegen step plus a spec that drifts the moment someone edits a route).

packages/contracts/src/{dto,trade,realtime,errors,settings}.ts

A pure domain package that performs no I/O

Every interesting decision — size this trade, is the spread acceptable, is the market open, is this symbol mapped — is a function of values passed in. The planner receives clocks, symbol specs, quotes and settings as arguments. That is why 45 planner tests can call it with hand-built snapshots and no database, on a weekend, in milliseconds.

Rejected: domain objects that fetch what they need. Convenient for a week, untestable forever after.

packages/domain/src/{copy-planner,risk,lots,pips,symbols,market,equity}.ts

Result<T, E> at the edges, exceptions for faults

The copy path is a decision pipeline where almost every step can legitimately decline: the spread is wide, the market is shut, the volume is below the broker minimum, the symbol moved. Those are data — they get a code, a log row and a trace. Exceptions are reserved for programming faults and infrastructure failure.

Rejected: throwing on a skip. It makes the common case look exceptional and tempts a blanket catch that swallows a real bug.

packages/domain/src/result.ts

6.2 Forex correctness

decimal.js for money and prices; never binary floating point

Position sizes are floored to a broker step and then validated against min/max. 0.1 + 0.2 !== 0.3 in binary floating point, and a volume that computes as 0.009999999 floors to zero — a silently dropped trade. Decimal arithmetic keeps the store honest; conversion to number happens only at the broker boundary.

Rejected: integer minor units. Prices are not the only quantity — volumes, lot steps, pip sizes and contract sizes all have different scales, and a single integer scale does not fit them.

packages/domain/src/{lots,risk,pips}.ts

A pip is derived from the symbol, not hard-coded

The naive rule — “a pip is 0.0001” — is wrong for JPY pairs (0.01), for 3-digit metals, for indices and for crypto. The rule implemented is the convention: on a 5-digit or 3-digit quote a pip is ten points, otherwise it is one point. This one function is why stops, spread gates and pip-based refiners are correct across the instrument list instead of only on EURUSD.

Rejected: a pipSize column in a lookup table. A table is a lie the first time someone adds a symbol.

packages/domain/src/pips.ts (28 symbol tests)

Volume: floor to step, clamp, and refuse to round up

Requested volume is floored to lotStep and clamped to minLot/maxLot, and a clamp writes a warning onto the log row. A volume that would floor to zero is skipped as VOLUME_BELOW_MIN — never rounded up, because rounding 0.004 lots up to the 0.01 minimum opens a position the user did not ask for.

Rejected: clamping sub-minimum volumes up to the minimum. It is the friendlier-looking choice and it is the one that quietly increases risk.

packages/domain/src/lots.ts

Five risk types, as explicit formulas, each returning a trace

Fixed Lot, Lot Multiplier, Balance Multiplier, Fixed Balance Multiplier, Fixed % Risk — the five the reference documents — plus Contract Alignment and the Lot Refiner as modifiers. Every computation returns the steps it took, which is what lets the dashboard explain a size rather than just display it.

Rejected: a single generic “sizing” function with flags. It becomes impossible to say which formula produced which number.

packages/domain/src/risk.ts — formulas in §8

Contract Alignment default-on for balance multipliers, off otherwise

The docs say “align contract sizes” without saying when. A Balance Multiplier copy of 1.0 lots of 100-oz gold onto a 1-oz CFD would be 100× the exposure — so for the balance-scaled types, alignment is on. Plain Lot Multiplier is a deliberate 1:1 lot ratio, so aligning there would break the user's stated intent.

Rejected: always-on (changes what Lot Multiplier means) and always-off with a warning only (leaves the dangerous case as the default).

packages/domain/src/risk.ts — see U4

Partial closes mirrored proportionally

The docs do not say (U5). Proportional is the choice that preserves the follower's risk ratio and is reversible by the user; FIFO is arbitrary from the follower's point of view.

Rejected: refusing partial closes, which would make a master's partial exit invisible to followers — a real risk difference.

packages/domain/src/copy-planner.ts, README (assumption)

Slippage tolerance in pips, converted to points at the terminal

Users and the reference product speak in pips; MT5's deviation is in points. One conversion, using the symbol's own pip size, in one place — so a 1.5-pip tolerance is 15 points on EURUSD and 15 on a 3-digit JPY quote (both 10 points per pip), not a fixed 15 everywhere.

Rejected: exposing points to the user. It is the unit that causes the mistakes.

integrations/mt5/TradeCopierBridge.mq5 · TcDeviation()

6.3 Data and durability

PostgreSQL + Drizzle, with migrations generated as explicit SQL and never auto-applied

The mapping is type-safe in TypeScript while the actual change is a reviewable .sql file. That split is the point: applying a schema change to somebody's database as a side effect of pnpm install is how data gets lost, so pnpm db:migrate is a deliberate release step.

Rejected: a lighter embedded store (the outbox needs SKIP LOCKED, which is a PostgreSQL gift) and an ORM that hides the DDL (nobody reviews what they cannot read).

packages/db/drizzle/0000_luxuriant_pixie.sql, 0001_amazing_the_renegades.sql

copy_commands is a durable outbox with a claim-based lease

A decision becomes durable the instant it is inserted, so a crash between deciding and executing loses nothing. Claiming is one atomic statement using SELECT … FOR UPDATE SKIP LOCKED … RETURNING, which is what lets several workers share the table with no lock manager and no Redis. Commands are serialised per account (position order matters) and parallel across accounts.

Rejected: an in-process queue (loses decided-but-unexecuted work on restart) and Redis (a second stateful dependency for semantics PostgreSQL already has).

packages/db/src/repositories/engine.ts · docs/ARCHITECTURE.md

Periodic work lives in a jobs table, claimed the same way

Daily resets, pruning and reconciliation must happen exactly once across API replicas without a leader election. Claiming job rows with the same lease primitive as commands gives that for free.

Rejected: a cron sidecar (a second scheduler that can drift from the app) and setInterval in every replica (N times the work).

apps/api/src/engine/{jobs,maintenance}.ts

Audit verbs are a text column typed by a TS union, not a Postgres enum

This was originally a pg enum, and it was wrong in a way that had no symptom at compile time (see defect 3). A union type gives the same editor safety while letting the vocabulary grow in a code change rather than requiring a migration first.

Rejected: keeping the enum and adding a cast at each call site — which is exactly the thing that hid the bug.

packages/db/src/schema/enums.ts · migration 0001

Raw SQL results are never trusted to be camelCase or Date-typed

Drizzle's db.execute() returns the raw driver result: snake_case column names, timestamptz as text (2026-10-19 05:41:48.243+00, which new Date() reads as local time). Every raw-claim path has an explicit mapper, plus shared toTimestamp helpers.

Rejected: a global casing transform and SQL aliasing — both hide which values came from where, and the timestamp issue survives either way.

packages/db/src/repositories/values.ts · see defect 2

6.4 The engine

Two phases: decide (and persist), then execute from the outbox

The decision and the broker call are separated by a durability boundary, so a broker outage pauses execution instead of losing intent, and the retry policy lives in one place instead of inside every call site.

Rejected: calling the broker inline from the ingest path — a slow broker then blocks the ingest of every other account.

apps/api/src/engine/{copy-pipeline,dispatcher}.ts

The engine's model of the slave is what the broker filled, not what was asked

On success the fill is written back onto the link (filledVolume, filledPrice, slaveTicket), and every later decision reads that. If the broker partially filled, the next close is proportional to reality rather than to the request.

Rejected: trusting the request. It diverges from the account on the first partial fill and never recovers.

apps/api/src/engine/dispatcher.ts

Every rule decision is stored as a trace on the log row

Each step records pass/adjust/skip with a detail string, so the dashboard can answer “why was this trade not copied, and by how much was that size adjusted” without anyone reading code. pnpm sim --verbose prints the same trace, which makes the copy path reviewable by a non-author.

Rejected: a boolean outcome plus a code. It cannot express “copied, but clamped from 0.05 to 0.01 lots”.

packages/domain/src/copy-planner.ts · execution_logs

Retries are bounded by time, not by attempt count

The reference says a copier retries an out-of-hours trade for up to 15 minutes (COPY_RETRY_WINDOW_MS), with exponential backoff capped at COPY_RETRY_MAX_MS. When the window closes, the command is dead-lettered with an actionable code and a notification — because “still trying” and “gave up” must be distinguishable.

Rejected: N attempts. With a variable poll interval, a count means an unbounded wall-clock delay in the worst case.

apps/api/src/engine/dispatcher.ts · oracles §3

Idempotency by deterministic requestId and delta-based link state

Re-delivering the same position snapshot must be a no-op, because a reconnecting agent will. The link is keyed by (master trade, follower), opens are keyed on disappearances and changes rather than on the stream, and every command carries a deterministic id — so a duplicated poll cannot produce a second position.

Rejected: trusting a sequence number from the agent. A reconnecting agent restarts its counters.

packages/domain/src/positions.ts · dispatcher

Reconciliation is scheduled on reconnect, and reopening is opt-in

When the socket reopens the agent has not pushed state yet, so the reconcile is deferred (~5 s) rather than run inline. It logs RECONNECT_MISMATCH for every divergence; actually reopening a position the slave lost is off by default (U7).

Rejected: reconciling inline on connect (races the first snapshot) and auto-healing (a delayed broker view becomes a doubled position).

apps/api/src/engine/{agents,reconciler}.ts

Equity protection is its own monitor with explicitly scoped actions

Drawdown and daily-loss rules are evaluated on their own cadence and can notify, disable_copier, close_copied_trades (an explicit ticket list resolved from the engine's links) or close_all_trades. Each firing writes an event row, a log line and a notification.

Rejected: putting the checks inline in the copy path. A protection rule must keep working when nothing is being copied.

apps/api/src/engine/equity-monitor.ts · see defect 6

6.5 Auth and secrets

JWT access tokens plus rotating refresh tokens hashed in the database

Access tokens stay stateless and short (15 min default); the refresh token is the stateful half, stored only as a SHA-256 hash, rotated on every use. Presenting an already-rotated token revokes the whole family — two holders of one refresh token means one is an attacker, so both sessions die.

Rejected: long-lived access tokens (no revocation story) and server-side sessions for everything (a DB round trip on every request).

apps/api/src/modules/auth.routes.ts · docs/SECURITY.md

scrypt and TOTP from node:crypto, not third-party crypto

The auth path has no third-party crypto dependency: scrypt (N=2^15, r=8, p=1, self-describing hash format so parameters can be raised later) and RFC 6238 TOTP implemented directly. Less supply chain in the one place where a compromise is total.

Rejected: pulling a TOTP library for ~60 lines of HMAC, and bcrypt/argon2 native modules for a two-second deploy problem.

apps/api/src/lib/{passwords,totp}.ts — 29 tests

AES-256-GCM with self-describing ciphertext; credentials never leave the server

Broker passwords and agent tokens are encrypted with a key that only exists in the environment. Ciphertext is v1.<iv>.<tag>.<payload>, a fresh nonce per encryption, and GCM detects tampering instead of returning garbage. A wrong key returns null rather than throwing, so a misconfigured deployment fails loudly. Nothing is ever returned — not masked, not fingerprinted.

Rejected: returning a masked value “for the UI”. The UI never needs it, so it is only ever a leak surface.

apps/api/src/lib/crypto.ts — 18 security tests

The dashboard's WebSocket uses a single-use ticket, never a token in the URL

A browser WebSocket handshake cannot carry a custom header, and a token in a query string lands in proxy logs and browser history. Instead the dashboard gets a 60-second single-use ticket over authenticated HTTPS and opens /api/v1/ws?ticket=….

Rejected: the access token in the query string, and cookies on the WS handshake (unreliable across browsers and proxies).

apps/api/src/lib/tickets.ts · docs/API.md § Realtime

One access token, two transports: tc_access cookie or Authorization: Bearer

The dashboard is a BFF with httpOnly cookies (no token in JS, no XSS exfiltration path); scripts, the agent and curl use a bearer header. One code path validates both, so tooling and browser cannot drift apart.

Rejected: localStorage tokens (XSS-exfiltratable) and a separate API key scheme for tooling (a second auth system to keep correct).

apps/api/src/plugins/auth.ts

6.6 The broker boundary

One BrokerConnector interface, three implementations

connect · getAccount · getPositions · getSymbols · placeMarketOrder · placePendingOrder · modifyPosition · closePosition · closeAll, plus an optional subscribe. A mock, a bridge agent and a remote RPC connector are interchangeable, which is what makes the whole copy path testable without a broker and makes a cTrader adapter a new file rather than a rewrite.

Rejected: a thin per-platform abstraction at the call sites. Broker quirks then leak into the engine.

packages/broker/src/types.ts

MT4/MT5 are served by a polling Expert Advisor, and that is stated as a limitation

MetaTrader has no supported server-side trading API. The honest options are a compiled DLL injected into the terminal, a screen-clicking robot, or an EA. The EA is chosen: no native code, works the same on MT4 and MT5, and auditable by the person whose money is at stake. The cost — minimum latency is the poll interval plus broker execution — is written down rather than glossed over (U1).

Rejected: claiming the vendor's 20–30 ms, and shipping a DLL. The first is untrue; the second is unauditable by the user.

docs/BRIDGE.md · integrations/mt5/

Mock accounts are mirrored into the hub's cache, so mocks and agents share one code path

This was a bug fix that became a design rule (defect 4). If a mock only feeds the engine's position view while the real path feeds a quote view, then the tests exercise a different decision path than production. Mirroring mock events into the same AccountCache means quote-age and spread checks behave identically — including, correctly, reporting STALE_QUOTE in a long mock session, because mock quotes are one-shot snapshots.

Rejected: exempting mocks from quote checks. The exemption is exactly where a broken check would hide.

apps/api/src/engine/{agents,connectors}.ts

Mock tickets are unique per connector instance

Links are reconciled by (account, ticket) and closed trades are unique on (account_id, ticket). A fixed mock ticket sequence meant a second simulation run reused tickets from the first, mis-attributing P/L and colliding on insert (defect 5). Prices stay seed-deterministic; only the ticket base is derived from wall-clock plus a hash of the account id.

Rejected: clearing history before every mock run only. That papers over the collision instead of making tickets what they are in reality — unique.

packages/broker/src/mock-connector.ts · tools/simulate-copy.ts

close_all is scoped by an explicit ticket list, resolved by the engine

“Close only the positions the copier opened” requires a request-id → ticket map, and that map lives in the engine's outbox on the server — the agent cannot resolve it. The first implementation sent request ids and the agent (correctly) refused, which meant Equity Protection's close copied trades could never work. Now the engine resolves its links and sends broker tickets (defect 6).

Rejected: widening the command to “close everything” on the agent, which would have liquidated the user's manual trades — a far worse failure than a no-op.

packages/contracts/src/realtime.ts · apps/bridge-agent/src/ea-link.ts

6.7 Monorepo, build and web

pnpm workspaces; packages consumed as TypeScript source

exports points at src/index.ts, so there is no “did you rebuild the package?” failure mode while developing. apps/api and apps/bridge-agent are bundled with tsup for deployment; apps/web uses transpilePackages.

Rejected: a build-order graph between packages. It buys a marginally faster cold build and costs a daily footgun.

Node ESM requires the .js extension even for TypeScript sources; Next's webpack needs to be told that ./x.js means ./x.ts when resolving inside a package. Stated because it is the kind of config that looks gratuitous until the first import fails.

Rejected: CJS. Everything here is modern and the ESM tax is one config line per consumer.

Tokens live in httpOnly cookies set by the server; the browser never holds one. It also means CORS is not part of the deployment story, and the WS ticket is issued server-side.

Rejected: browser-direct API calls with tokens in JS storage.

6.8 Testing

Integration tests run against real PostgreSQL, and refuse to run anywhere else

The outbox's claim statement, its leases and the migration ledger are the parts most likely to be wrong, and none of them exist in a mock. The suite skips entirely when TEST_DATABASE_URL is unset and the harness refuses any database whose name does not end in _test.

Rejected: SQLite in-memory. It would test a different database than the one in production.

apps/api/test/helpers/database.ts

Integration fixtures use crypto (BTCUSD), and the API project runs serially

A forex fixture would make the suite fail on a weekend or across the 21:00–22:00 UTC rollover — a test that fails for calendar reasons teaches people to ignore failures. And because each DB suite rebuilds the schema, the suites run in a single fork; parallel files would race on the same database.

Rejected: a shared migrated database per run. The reset cost is small and correctness is worth it.

Rejected: snapshot tests for sizing. They would freeze a wrong formula in amber.

7. Six defects, found by running it

This section is the most useful one. Four of these six lived in code that compiled, type-checked and read as correct. They were found by executing the thing against a live database, not by reviewing it. That is the argument for running what you build before you describe it as done.

1 · The API never booted: @fastify/cookie was registered twice

Symptom: The decorator 'serializeCookie' has already been added at startup. The plugin was registered once in server.ts and again inside authPlugin. Worse: buildServer() had therefore never actually run in any test, so a green type-check was covering for a server that could not start.

Fix: one registration in server.ts; authPlugin declares dependencies: ['@fastify/cookie'] instead, which is Fastify's proper way to express the ordering need. A 401 in the auth-flow tests is what sent me looking.

ff8411d · apps/api/src/{server.ts,plugins/auth.ts}

2 · Raw SQL claim rows came back snake_case and text-typed

Symptom: Cannot read properties of undefined (reading 'getTime') on the retry path. Drizzle's db.execute() returns the driver's raw result: account_id not accountId, and timestamptz as the string 2026-10-19 05:41:48.243+00, which new Date() parses as local time — a silent off-by-timezone bug waiting behind the crash.

Fix: an explicit mapper per raw path (toClaimedCommand, toClaimedJob, toClaimedNotification) plus shared toTimestamp/toTimestampOrNull helpers. The rule now: no raw result is ever trusted to be camelCase or date-typed.

e6fae45 · packages/db/src/repositories/{engine,values}.ts

3 · Every audit insert failed at runtime, hidden by an as never cast

Symptom: none visible from the type-checker. The audit_logs.action column was a pg enum with values that had never been reconciled with the call sites, and every caller passed a dotted verb like user.login. An as never cast silenced the compiler, so nothing failed until an insert actually ran — at which point every audit write raised a Postgres enum error. The audit log was, in effect, empty.

Fix: make the column text, type it in TypeScript as an AuditAction union, and drop the enum in migration 0001. Lesson recorded: a cast that suppresses a compiler error on a value crossing a boundary is a bug you have agreed to find in production.

e6fae45 · packages/db/src/schema/enums.ts · drizzle/0001

4 · Mock accounts were unpriced, so every copy skipped as STALE_QUOTE

Symptom: the simulator produced no copies at all, each one logged as STALE_QUOTE. The engine's quote-age and spread checks run against the hub's account cache; mock positions reached the engine, but mock quotes never entered that cache. Type-checked beautifully; did nothing.

Fix: createMock mirrors events into the same AccountCache and seeds one quote per symbol, so mocks and real agents take an identical decision path. This turned into a design rule (see §6.6): a test path that differs from production is not a test.
Note on what remains “wrong”: mock quotes are one-shot snapshots, so a long-running dev session will correctly start reporting STALE_QUOTE. That is the rule working, not a bug, and it is documented rather than papered over.

dcde35a · apps/api/src/engine/{agents,connectors}.ts

5 · Reused mock tickets mis-attributed P/L and collided on insert

Symptom: a second simulation run reported profit against links whose tickets belonged to the first run. Links are reconciled by (account, ticket) and account_closed_trades is unique on (account_id, ticket), so reused tickets are both a correctness bug and a constraint violation. Mock tickets started from a fixed constant.

Fix: MockConnectorOptions.ticketStart, derived per instance (10^10 + (Date.now() % 10^9)·1000 + hash(accountId) % 1000). Prices stay seed-deterministic so assertions stay stable. Also added clearCopierHistory() so a repeat run is not polluted by links to tickets that no longer exist.

dcde35a · packages/broker/src/mock-connector.ts

6 · Equity Protection's “close copied trades” could never work

Symptom: found while writing the EA and tracing parameter vocabularies. RemoteConnector.closeAll converted the engine's ticket list into originRequestIds and expected the agent to resolve them into broker tickets. It cannot — that map lives in the engine's outbox. Two connectors also used different parameter names for the same call ({reason, magic, tickets} vs {comment, filterMagic, originRequestIds}).

Why it mattered: a safety feature that silently does nothing is worse than an absent one, because you rely on it. The earlier hardening (refusing the command rather than widening it to “close everything”) was correct but left the feature dead.

Fix: the ticket list now travels as a ticket list — commandParamsSchema carries tickets, the agent forwards it, and the EA closes exactly those positions, with filterMagic and “everything” as the coarser scopes that Equity Protection's close all trades uses.

ba1f1ad · packages/contracts/src/realtime.ts · apps/bridge-agent/src/ea-link.ts

The pattern. Three of the six (#1, #3, #4) were invisible to the type-checker and made a feature a no-op rather than an error: a server that could not start, an audit log that recorded nothing, a copier that copied nothing. None of them would have been caught by more tests of the same kind — only by running the path end to end against the real database. The remaining three (#2, #5, #6) were contract mismatches: two sides of a boundary each internally consistent, disagreeing about a name or a unit.

One more correction, in the other direction: the code was right and my docs were wrong

When writing the sizing table for docs/MANUAL-STEPS.md I drafted “FIXED_BALANCE_MULTIPLIER = master lots × (fixedMasterBalance ÷ masterBalance) × balanceMultiplier” and “LOT_MULTIPLIER = master lots × lotMultiplier”. Both were wrong against packages/domain/src/risk.ts: the multipliers are percentages (100 = 1:1), and the fixed-balance variant divides the slave balance by the fixed reference — dividing by the live master balance would defeat the entire point of pinning a reference. So the exercise of writing the formulas down was itself a verification step, and it caught the documentation rather than the code. It also corrected docs/API.md, which had attached the “100% = 1:1” note to the wrong risk type.

8. The sizing formulas

Written out because a wrong formula here is a wrong position size, and the reference documentation describes the risk types by name rather than by formula. All five are in packages/domain/src/risk.ts, each returning a trace of the steps it took.

Risk typeFormulaWhen you would use it
LOT_MULTIPLIERmaster lots × (lotMultiplier ÷ 100)Proportional to the master; 100 = 1:1, 50 = half, 150 = 1.5×
FIXED_LOTfixedLotEvery copy the same size
BALANCE_MULTIPLIERmaster lots × (followerBalance ÷ masterBalance) × (balanceMultiplier ÷ 100)Risk stays proportional to capital as the follower's balance moves
FIXED_BALANCE_MULTIPLIERmaster lots × (followerBalance ÷ fixedMasterBalance) × (balanceMultiplier ÷ 100)Same, against a pinned reference instead of the master's live balance
FIXED_PERCENT_RISK(followerBalance × percentRisk ÷ 100) ÷ (stopLossPips × pip value per lot)Risk a fixed share of the follower's balance per trade; needs a stop loss (master's, or fixedStopLossPips)

Two modifiers sit on top of the result:

  • Contract Alignment multiplies by masterContractSize ÷ slaveContractSize; default-on for the balance-scaled types, off otherwise, with a warning log when sizes differ and it is off. See U4.
  • Lot Refiner is an additive offset applied last, and may be negative — which is how a user says “always 0.02 lots less than the master”.

Then the broker's constraints: floor to lotStep, clamp to minLot / maxLot (warning on the log row), and skip as VOLUME_BELOW_MIN if the result floors to zero. Where a pip value cannot be converted into the account currency, the computation is marked degraded and says so rather than assuming a rate.

12. What I would fix next

In the order I would actually do them, which is roughly “de-risk the unverified side first”:

  1. Compile and dry-run the EA against a demo MT5 account. InpDryRun = true exists for exactly this: the engine sees fills against a fake ticket, so the whole loop is observable without a single real order. Nothing else in the repo is as unverified as this file.
  2. Fix the parameter vocabulary between the connectors. BridgeConnector.closeAll and RemoteConnector.closeAll still take the same argument under two different names ({reason, magic, tickets} vs {comment, filterMagic, tickets}). Defect 6 made them agree on the wire; making them agree in TypeScript would stop the next divergence.
  3. Replace the in-process rate limiter and ticket store with a shared store before running more than one API replica. The interfaces are already narrow (consume, issue/consume) — this is a drop-in, not a redesign.
  4. An MT4 .mq4 EA. Same polling contract, different order API. It is the most-requested platform in this market and the contract already supports it.
  5. Email verification and password reset, which need an outbound mail provider and a single-use token store. This is the largest gap between “runs” and “operable by strangers”.
  6. A second real BrokerConnector (cTrader or Match-Trader) to prove the seam is genuinely generic rather than MT5-shaped with an interface in front of it. Interfaces are only proven by a second implementation.
  7. Alert on queue.depth and queue.oldestQueuedAgeMs. A growing queue means the broker side is slow or an agent is offline, and it will not fix itself. The numbers are already in GET /api/v1/health; nobody is watching them.
